# Stretch Goals (optional) — what was built, and why the core made it cheap

The brief is explicit: "Only if you have time and a solid core. Pick at most one or two — depth over breadth." This project built more than that — three of six stretch goals in full, a fourth partially, two deliberately left out — which is worth defending directly rather than left to speak for itself, since it cuts against the brief's own stated preference for restraint.

The honest version of that defense is not "we had time, so we did more." It's narrower and more falsifiable: **every stretch goal actually built here was a near-zero-marginal-cost consequence of a specific decision already made for the required core**, not separate feature work bolted on afterward. Where that wasn't true — where a stretch goal would have required new abstractions, not just a new consumer of existing ones — it was left out. This document names the specific decision behind each one, so that claim is checkable rather than asserted.

## Built in full

### Agent-facing capability interface

**What's built.** Every `verified`/`approved` artifact is exposed two ways: through the Anthropic SDK directly (`npm run catalog:demo`) and as a genuine MCP server (`@modelcontextprotocol/sdk`, real `tools/list`/`tools/call` JSON-RPC over HTTP, `npm run mcp`) — vendor-neutral, not tied to one agent framework. A live invocation is demonstrated both ways: Claude picks a capability from the catalog, supplies typed arguments, and the deterministic replay engine (not the model) executes it; a raw `curl` against the MCP endpoint gets the identical result over the wire protocol.

**Why the core made this cheap.** The capability artifact is already a Zod schema (`CapabilityDefinitionSchema`) with declared, typed `inputs` and `outputs`. `zod-to-json-schema` — already a dependency, already used to emit `docs/capability.schema.json` for artifact validation — turns that same schema into the `input_schema` an Anthropic tool definition or an MCP tool needs. `src/catalog/index.ts` is about 100 lines because the actual hard part (a typed, self-describing contract) was already the artifact schema's job, done for a different reason (human review) that happened to be exactly what an agent-facing interface also needs. This is the cleanest case of "the core wasn't just reused, it was *the same artifact* doing double duty."

### Canonicalization and cross-tenant reuse

**What's built.** Both halves of this bullet, not just one. Canonicalization: the compiler derives `scope.allowedRoutes` from routes actually visited during its own live verification replay (`/member/12345/accounts` → `/member/:memberId/accounts`, by exact-matching path segments against declared input values), not a hand-typed list. Cross-tenant reuse: the same verified artifact, recorded against one target-app instance, replays successfully against a second, differently-labeled instance of the same underlying vendor product (`TenantBinding`, `tenants/credit-union-b.json`) via override alone — no re-recording — live-verified, not just designed.

**Why the core made this cheap.** Canonicalization reuses the *exact same* live-replay-through-`resolveTarget()` mechanism the compiler already runs for target-uniqueness verification (§3 of `REPORT.md`) — it just also records which concrete route that replay visited, instead of only whether a target resolved. Cross-tenant reuse is a direct consequence of `targetRegistry` being keyed by `semanticPurpose` rather than being inlined per-step: a `TenantBinding` only had to declare *one new concept* (an override map with the identical key) to get "swap how a control is found, leave everything else untouched" for free — the alternative (targets inlined directly on each step) would have needed a binding to reach into and rewrite arbitrary step bodies, a much larger and much less safe mechanism. Recompiling with canonicalization live also surfaced two real defects before either shipped (a policy matcher that didn't understand `:name` segments; a checkpoint proposal that referenced a page state that no longer existed) — both fixed and re-verified, documented in `REPORT.md` §3 and `docs/slices.md`.

### Multi-run stability

**What's built.** `scripts/stability.ts` replays a capability N times against the same input and reports a success rate plus per-step rung consistency — a step resolving via a *different* candidate strategy across otherwise-identical runs is a real drift signal even when every individual run succeeds. Run for real: 5/5 successes, zero rung drift, against the verified `member.read-savings-balance@2` artifact.

**Why the core made this cheap.** `recordedRung` already exists on every `Target` and `matchedRung` is already returned on every `perform()` outcome — both computed for an unrelated reason (drift detection against the *compiled* artifact, §4 of `REPORT.md`). Stability checking is aggregation over a field the replay engine was already producing on every single run; no new instrumentation was needed, only a loop and a summary.

## Partially built

### Confidence & approval

**What's built.** The `status` lifecycle (`draft → verified → approved → deprecated/disabled`) is real and enforced at more than one layer: `promote.ts` only flips `draft → verified` after a human has actually looked at a verification replay (it doesn't run the replay itself — see `REPORT.md` §1's framing of why auto-compile deliberately doesn't auto-verify); the capability catalog (`loadCatalog()`) excludes anything that isn't `verified`/`approved` from agent-facing discovery entirely — an agent literally cannot see, let alone invoke, a `draft` capability through the catalog or MCP. `replay-tenant.ts` independently refuses to bind an unverified capability as a cross-tenant base. Multi-run stability (above) is the "score by how reliably it replays" half of this bullet, standing on its own.

**What's not built, and why left that way rather than retrofitted.** The brief's phrasing also implies gating *unattended replay itself* — not just agent-catalog discovery — on approval state (e.g., `npm run replay --mode UNATTENDED` refusing a `draft` artifact directly). Adding that check to `scripts/replay.ts` was actually attempted while writing this document, then deliberately reverted: `member.read-savings-balance.v1.json` (and both sub-account capabilities) are intentionally-`draft`, richly-annotated reference artifacts that essentially every demo and evidence directory in this repo replays in `UNATTENDED` mode by default — the *hand-authored* artifact with the full error/outcome taxonomy wired in, kept deliberately separate from the *compiled-and-promoted* `v2`/`v3` lineage (§ "The end-to-end thread" in `README.md`). Retrofitting a blanket CLI-level gate would have required either promoting artifacts that were deliberately kept `draft` as teaching/reference material, or rewriting most of this project's existing, already-verified demo commands to add `--mode ATTENDED` — real, live-verified evidence put at risk for a stretch goal explicitly scoped to "at most one or two" in the first place, and a completeness gain the catalog-level gate already delivers for the case that actually matters (an *agent* invoking a capability unattended). Left honestly partial rather than silently claimed complete.

## Deliberately not built

### Code generation

Emitting a runnable test/page-object file from an artifact was not attempted. Unlike the other stretch goals, this one doesn't fall out of an existing core decision — it would need a genuinely new component (a code generator with its own templating and output-language concerns) rather than a new consumer of the artifact schema, replay engine, or targeting ladder. It was the lowest-value use of remaining time against the brief's own "the load-bearing pieces are the artifact schema, deterministic replay, and the safety/escalation model" steer, and was cut for that reason, not for lack of a design.

### Assisted fallback

`assistedRepair` exists in the schema (`{enabled, maxSteps: 1, requiresTenantPolicy}`), is validated, and ships `enabled: false` on every artifact in this repo — but the actual bounded, policy-checked single-step LLM recovery behind it was never implemented. This is the one stretch goal whose schema seam was built (deliberately, so the *next* increment is "implement the behavior a field already reserves," not "redesign the schema to allow for it") while the behavior itself was cut. Already named in `REPORT.md` §7's Cuts as the first item in "what we'd build next," for the same reason it wasn't attempted here: it is the stretch goal most likely to reintroduce exactly the kind of open-ended, per-step LLM judgment call the rest of this system's design works to keep out of the default replay path, and doing it *safely* (bounded, policy-checked, evidenced, never open-ended) deserves more design attention than remaining time allowed to give it credibly.

## The honest caveat

Building more than "one or two" is a real deviation from the brief's own explicit guidance, and a reviewer who weighs "depth over breadth" strictly is not wrong to discount it. The defense above is offered as evidence for a narrower claim than "more is better": that a solid, well-abstracted core (a semantic-purpose-keyed target registry, a typed and self-describing Zod artifact schema, a replay engine that already produces the exact signals stretch goals 1/5/6 needed) makes several stretch goals cheap enough that building three of them cost less engineering effort, and introduced less net-new surface area to get wrong, than building any *one* of them would have cost against a less deliberately-designed core. Whether that trade was the right one to make under "pick at most one or two" is exactly the kind of judgment call this document exists to make checkable, not to pre-decide.
