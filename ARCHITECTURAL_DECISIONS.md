# Architectural Decisions — interface_replay_ai

The brief is explicit that seven areas are the implementer's call, with one exception that is not negotiable (a genuine LLM-driven discovery run) and one standing allowance (mock a seam deliberately, document it). This document takes each in turn: the decision, the reasoning behind it, the alternatives actually considered and why they lost, and where the evidence for the decision having worked lives. It is a defense, not a changelog — `docs/slices.md` has the build-order history; this has the reasoning.

---

## 1. Language, runtime, and frameworks

**Decision.** TypeScript (strict), Node.js, `tsx` for direct execution in development, a real `tsc` build as a correctness gate, Vitest for unit tests, Express for every HTTP surface (target app, operator console, MCP server), Zod for every schema.

**Why.** The project's center of gravity is a *schema* — the capability artifact — not a UI or a data pipeline. Zod makes that schema the single source of truth for three consumers that would otherwise drift independently: the TypeScript types (`z.infer<typeof X>`), runtime validation (`X.safeParse(...)`, used identically at compile time, replay time, and artifact-load time), and the JSON Schema handed to Anthropic's tool-use API and to MCP's `tools/list` (`zod-to-json-schema`). Any language without a library doing this in one place would need two or three hand-maintained schema representations kept in sync by discipline alone — exactly the kind of drift this project's own "declared but never exercised" gaps (found and closed repeatedly during review) already show is a real risk, not a theoretical one.

Node was the practical consequence of that choice, not an independent one: Playwright's best-supported, most idiomatic binding is Node/TypeScript (the Python and Java bindings exist but are secondary citizens for newer API surface), and Anthropic's and MCP's official SDKs are both TypeScript-first. Picking Node meant every layer of this system — target app, discovery loop, compiler, replay engine, operator console, MCP server — lives in one language, one package, one `npm install`, with no cross-language IPC boundary to design or debug.

Express, specifically, over a heavier framework (Next.js, NestJS, Fastify-with-plugins): every HTTP surface in this project is either a demo fixture (the target app) or a thin, auditable shim over a real mechanism (the operator console over CDP, the MCP server over the catalog). A project whose selling point is "read the code and verify the claim yourself" benefits from routes that are five lines of plain `app.get(...)`, not framework conventions a reviewer has to already know.

Vitest over Jest: native ESM and TypeScript with no transpilation configuration, and this project's test suite is fast enough (72 tests, under a second) that startup overhead differences would have been the dominant cost with a heavier runner.

**Alternatives considered.** Python (mature Playwright binding, but a second-class one relative to Node's; would have split the MCP/Anthropic SDK ecosystem into two languages for no benefit). A compiled language (Go, Rust) for the replay engine specifically, for raw performance — rejected because replay's bottleneck is network/page-load latency, not CPU, and a second language would have reintroduced exactly the cross-language schema-sharing problem Zod was chosen to avoid.

**Evidence.** `package.json`; `npm run build` (a clean `tsc -p .` gate) and `npm test` (72/72) both run as part of every change in this session's history, not just at the end.

## 2. LLM provider / model, and how the agent loop is prompted and structured

**Decision.** Anthropic Claude, model `claude-sonnet-5`, via the official `@anthropic-ai/sdk`. A closed tool vocabulary (`navigate`, `click`, `type`, `extract`, `finish`, `request_human`) with `tool_choice: {type: 'any'}` forcing exactly one tool call per turn — never free text the loop has to parse or interpret. Every tool input is Zod-validated (`DiscoveryActionSchema`) before it is allowed to touch the adapter.

**Why the vendor.** Two independent reasons converged on Anthropic rather than making it an arbitrary pick. First, technical: discovery needs a model that is both a reliable structured tool-caller (the whole loop depends on `tool_choice: any` actually producing a well-formed tool call every turn, not a stray text response the loop would then have to handle as an error case) and, for the set-of-marks grounding this project uses, vision-capable — Claude satisfies both without a secondary vision-only model bolted on. Second, and just as real: the agent performing this take-home *is* Claude, running inside Claude Code — using the same vendor's SDK directly for the system's own discovery calls avoided introducing a second vendor's auth, quota, and rate-limit surface purely to prove a point about neutrality that the architecture already proves a better way (see below).

**Why this doesn't create vendor lock-in where it would matter.** The system is deliberately *not* Anthropic-specific at either of its two real boundaries. Replay makes zero LLM calls of any vendor — enforced structurally, not by convention (`tests/replay/no-llm-import.test.ts` scans the replay/surface/policy modules for any LLM-client import and fails if one is added, on purpose or by accident). And the capability catalog is exposed over genuine MCP (`@modelcontextprotocol/sdk`, real `tools/list`/`tools/call` JSON-RPC), which is vendor-neutral by construction — any MCP-compatible agent (Claude, GPT, a local model, a hand-rolled client) can discover and invoke a capability with no Anthropic dependency at all, verified with both a browser test UI and raw `curl`. Anthropic-specificity is confined to exactly the one place the brief itself demands an LLM be involved: the discovery run.

**Why this model, not a larger or smaller one.** Discovery's decisions are narrow, well-specified choices over a small closed action space (which numbered mark to click, what to type, whether the goal is met) — not open-ended multi-step reasoning. `claude-sonnet-5` is more than sufficient for that action space, and the more important property for this project was *reliability of the tool-use contract* (never wandering off-schema) over raw reasoning depth. This is also a genuinely low-stakes choice architecturally, for a reason worth stating plainly: discovery is compiled away by the compiler into a deterministic artifact and never runs again for that capability — model choice here trades exploration quality against per-run cost, not production latency, since production traffic never touches an LLM at all.

**How the loop is structured, and why not a looser ReAct-style prompt.** Observe (a screenshot with numbered marks over every visible control, from `observeWithMarks`) → decide (one tool-use turn) → act (through the *same* policy-gated `performDiscoveryClick/Navigate/Type/Extract` methods a desktop adapter's discovery equivalent would also route through) → repeat, with five explicit, independently-checked stop conditions (max steps, wall-clock timeout, the same page fingerprint repeating across turns, the model's own `finish`/`request_human`, a policy denial) rather than one loose "keep going until it seems done." A closed tool vocabulary with Zod-validated arguments means every model output is mechanically checkable before it can touch a live system — the identical "structured, not free text" discipline the capability artifact schema itself follows, applied one layer earlier. An unconstrained chain-of-thought prompt asking the model to describe what to do in prose, then parsing that prose for an action, was rejected outright: it would have reintroduced exactly the ambiguity-tolerant, best-effort interpretation this project's entire replay path is designed to eliminate, one step earlier in the pipeline than replay.

**Prompt-injection and secret hygiene, as part of "how you prompt."** The model is told an input's *name* only, never its value (`{{inputs.memberId}}`, never `12345`) — the placeholder crosses into a real value only inside `perform()`, below the logging boundary. A pre-flight guard refuses to launch at all if a goal string contains a raw sensitive value verbatim, closing the one leak vector the placeholder convention alone doesn't (a caller writing "look up member 12345" instead of using the placeholder) — found as a real leak during development, not designed defensively in the abstract.

**Evidence.** `src/discovery/model.ts`, `src/discovery/actions.ts`; every `evidence/discovery-*/` directory in this repo is a genuine, non-simulated Sonnet 5 tool-use transcript (`trace.jsonl`) against the live target app — several independent runs across this project's development, not one cherry-picked example. See "the one non-negotiable" below.

## 3. Computer-use technology

**Decision.** Playwright, driving a real Chromium instance launched with an exposed CDP debugging port (`chromium.launch({args: ['--remote-debugging-port=...']})`), not Playwright's own `launchServer()`/`connect()` pairing.

**Why Playwright over Puppeteer or Selenium.** Playwright's locator API is accessibility-tree-first (`getByRole`, `getByLabel`, `getByText`) in a way that maps directly onto the `(role, accessibleName)` vocabulary this project's targeting ladder needs at its most portable rungs — Selenium has no comparable native accessibility-locator API, and Puppeteer's is thinner and less idiomatic. Cross-browser support (Chromium/Firefox/WebKit) from one API also means the target-app surface isn't accidentally coupled to one rendering engine's quirks.

**Why real CDP, specifically, and not Playwright's higher-level multi-client primitive.** This was verified empirically before being relied on, not assumed. A throwaway script confirmed that a second `chromium.connect(wsEndpoint)` call against a `launchServer()`-started browser gets an *isolated* view with zero contexts, even though the first client's context demonstrably still exists — that pairing is built for sequential reuse across test runs, not concurrent multi-client access. It would have silently broken the entire human-handoff mechanism (§3.6) if discovered after building on top of it instead of before. Real CDP (`--remote-debugging-port`, `chromium.connectOverCDP()`) is what DevTools-style tooling actually uses for this, and it was confirmed directly to share contexts and pages across genuinely separate, simultaneous OS processes — which is the literal requirement behind "operate the same live session," not a looser approximation of it.

**Why not a CUA/agent SDK (a vision-and-coordinates computer-use tool) for either path.** For replay, a CUA-style tool is disqualified outright: it is LLM-in-the-loop and coordinate/vision-driven by design, which directly contradicts "replay must not invoke the LLM for decisions." For discovery, a full screen-pixel CUA loop was considered and rejected in favor of the cheaper, more precise set-of-marks + accessibility-tree approach this project actually uses: the web surface exposes real structure (DOM, ARIA, roles), and reducing that structure down to raw pixels and coordinates before reasoning about it throws away information a full CUA loop would then have to re-infer from vision alone, at higher cost and lower precision. A pure-vision CUA-style approach remains the right *fallback* for a surface that genuinely offers nothing else — Citrix, a legacy bitmap-rendered desktop client — and that fallback is named explicitly (not silently assumed away) in `COMPLIANCE.md`'s surface-abstraction section as the eighth, unbuilt rung this design would add for that specific case.

**Why not raw OS-level automation (coordinate clicking against the physical screen).** Zero portability across screen resolutions or window positions, and zero semantic content about *what* was clicked — it fails the brief's own "reasoning about robustness" ask by construction, since there is nothing to reason about beyond a coordinate pair. This project's own weakest, explicitly-flagged-nonportable rung (`visible_text`, a raw text match) is already one step more robust than coordinates and is treated as a last resort, never a primary strategy; true coordinate-only targeting was never seriously considered as anything but the absolute final fallback a real production system would need and this demo doesn't.

**Evidence.** `src/surface/adapter.ts`'s header comment documents the `launchServer()`/`connect()` finding directly; the human-handoff evidence in `evidence/replay-handoff/` and `evidence/discovery-handoff-demo/` is the live proof the CDP choice actually delivers same-session control, not simulated control.

## 4. Target application

**Decision.** A locally-built, self-hosted, deliberately old-school synthetic banking app (`target-app/`) — server-rendered HTML, table-based layout, no test IDs, no ARIA attributes, form labels associated only by table-cell adjacency, one deliberately hostile iframe, synthetic members and a synthetic operator credential (`demo-pass-1234`, printed in every README example, never a real secret).

**Why a built local app over a public demo/sandbox site.** Three reasons, each sufficient alone. First, stability under repeated iteration: this project needed dozens of live, repeatable runs across its development — a public site's markup, uptime, and rate limits are outside this project's control, and a flaky or rate-limited target would have made "live-verify every claim" (this project's own standing discipline) impractical rather than merely inconvenient. Second, coverage: the brief's own required failure taxonomy (a validation error, a not-found result, a permission denial, an unexpected dialog, a session timeout, a slow/failed load) needs deterministic, on-demand fixtures for every one of those six conditions — no public sandbox offers all six on command, and several (a permission-denial banner, a session dropping mid-flow) aren't naturally occurring conditions a public demo site would ever expose at all. Third, the brief's own explicit risk framing: no real credentials, no real PII, respect for a third party's terms and rate limits are all real constraints that a wholly synthetic, self-owned app sidesteps by construction rather than by care.

**Why deliberately hostile markup, rather than a clean modern app.** The brief names this explicitly as the harder, more representative case ("if you want to lean into the legacy/no-clean-DOM reality"), and it is the case that actually stress-tests the targeting ladder's weaker rungs. A clean React app with `data-testid` attributes everywhere would have let rung 1 (`semantic_id`) resolve every target trivially, proving nothing about rungs 2–7. This target app's member-identifier field, for instance, genuinely fails role-based resolution (rung 2) on every real run and falls through to the table-cell-adjacency heuristic (rung 3) — confirmed live, not asserted — which is the actual condition this project needed to prove the ladder's fallback behavior against.

**Why this specific flow shape, and why it grew a second one.** The brief suggests two representative shapes: "search → detail → action" and "a multi-field form with a confirmation step." This target app builds both, not just one: the core read flow is exactly the first shape (member search → member detail → accounts, deliberately routed through an iframe to force frame-traversal targeting); the sub-account create/close flow (added while closing the risk-class gap in §3.4) is exactly the second shape (a type-select + nickname form → a confirmation screen, plus a second irreversible confirm-with-warning flow). Building both wasn't strictly required by any single bullet, but it meant every suggested shape in the brief is demonstrated against real markup rather than argued about in the abstract.

**Evidence.** `target-app/templates.ts`'s own header comment states the no-clean-markup intent directly; `README.md`'s member-ID verification table lets a human browse every one of these conditions live, in their own browser, without touching any script.

## 5. The artifact schema and how it's stored/serialized

**Decision.** Zod-defined (`src/contracts/capability.ts`), serialized as plain JSON, one file per capability version on disk (`capabilities/<capabilityId>.v<n>.json`), versioned by git commit history rather than a database.

**Why JSON, and why one file per version rather than a mutable record.** The brief requires the artifact be reviewable by a human before it's trusted — a JSON file opens in any editor, diffs cleanly in a code review tool, and needs no client or query language to inspect. It is also exactly the wire format MCP's `tools/call` already needs to return, so there is no translation layer between "the artifact at rest" and "the artifact over the protocol a calling agent actually uses." One immutable file per version (rather than one mutable row updated in place) makes "approved artifact versions are immutable" (a scaling invariant this project already commits to in `docs/phase-2-scale.md`) true for free, as a property of git itself, not a rule a database schema has to separately enforce with a trigger or an application-layer check.

**Why flat files over a database, at this project's scale.** A database buys query flexibility and concurrent-write safety — neither of which this project's single-tenant, handful-of-capabilities demo needs. Introducing one would have added a service to run, a connection string to manage, and a migration story, for a benefit (indexed lookup across thousands of capabilities) that doesn't exist yet at this scale. This is explicitly named as a "simpler is fine if justified" choice, with the scale-up path already reasoned through rather than deferred: `docs/phase-2-scale.md` specifies the exact relational shape (`tenantId, capabilityId, applicationInstanceId → exact artifact version`, a bounded four-hop join) a production catalog would use, and is explicit about *not* reaching for a graph database or a vector store for that lookup even at hundreds-of-tenants scale.

**Why Zod as the schema language, restated for this specific decision.** Beyond the types/validation/JSON-Schema triple-duty already covered in §1, Zod's `.superRefine()` was what made a genuinely structural requirement — "an object-shaped output needs a producer named for every declared property" — enforceable at parse time rather than as a separate, easy-to-forget runtime check scattered across the compiler and the replay engine. The schema *is* the correctness gate here, not documentation of one.

**Evidence.** `scripts/validate-artifacts.ts` (run as a standing regression check after every schema change in this session); `capabilities/*.json` are real, git-tracked files a reviewer can open directly.

## 6. How determinism is achieved on replay

**Decision.** An ordered list of typed target strategies per control, tried in declared order, stopping at the first strategy resolving to **exactly one** match (more than one match is reported as `ambiguous` immediately, never resolved by falling through to a weaker rung); structured `Condition` objects (never free-text or `eval`-style expressions) for every precondition, postcondition, and checkpoint; a single bounded-polling primitive (`waitForCondition`) as the only form of waiting anywhere in the replay path — no unconditional sleeps; business-outcome probes checked *before* postconditions at every step boundary; and a structural guarantee (a scanning unit test, not a code-review convention) that the replay engine never imports an LLM client at all.

**Why an ordered exact-match ladder, not a confidence-scored resolver.** This was an explicit, considered rejection of how some commercial RPA tools (and vision-based matching generally) work: score every candidate against the live page, accept the highest score above a tunable minimum-confidence and uniqueness-delta threshold. That design was rejected because it reintroduces, one layer below capability *selection*, the exact non-determinism this project already rejects at the *selection* layer for an identical reason (`docs/phase-2-scale.md`'s argument against embedding-based capability lookup) — a 0.91-vs-0.89 confidence gap silently deciding which control got clicked is no more auditable than a similarity score silently deciding which capability ran. An ordered, boolean-outcome ladder is slower to author (a human has to declare the fallback order deliberately) but makes replay's behavior fully determined by the artifact file on disk, with no threshold anyone can retune out from under it later. For a capability that can move money, that trade favors auditability over resolver cleverness.

**Why bounded polling, not Playwright's own auto-wait alone or a fixed sleep.** Playwright's auto-wait solves a narrower problem (is this element attactionable right now) than what replay actually needs to wait for — a capability-author-declared *business* condition (the postcondition, a business-outcome banner, the checkpoint), which has no generic DOM-actionability signal to key off. A fixed sleep is the alternative every flaky-test guide warns against for good reason: too short and it's flaky, too long and every replay pays the worst-case latency even on the common fast path. `waitForCondition`'s short-interval poll against the *same* structured-condition evaluator every other check in the engine already uses gives a bounded worst case without either failure mode, and reuses one code path instead of three ad hoc waiting strategies.

**Why business outcomes are checked before postconditions, structurally, not as a special case.** The brief names conflating a business result with a broken step as the most common design mistake in this space. Checking every declared `knownOutcome` at each step boundary *before* evaluating that step's own postcondition means a legitimate "no such member" result can never be misread as "the postcondition failed, this run is broken" — verified directly, not just designed: replaying a nonexistent member ID is caught and returned as a named outcome at the search-submit boundary, before the engine ever gets to a postcondition that would technically also hold true for other reasons.

**Why a compiler that replays live rather than one that asserts uniqueness by inspection.** The compiler calls the *exact same* `resolveTarget()` the replay engine itself uses, live, against a real page, and only writes a target into the artifact after confirming it resolves to exactly one match — a target is never accepted on the strength of "this selector looks specific enough." This closed a real defect during development (a checkpoint proposal that referenced a control from an earlier page state, invisible on the actual final page) that a static, non-executing check would have missed entirely.

**Evidence.** `tests/replay/no-llm-import.test.ts`; `REPORT.md` §3's "real defects caught by reading raw evidence" list; every `evidence/replay-*/` directory's `events.jsonl` shows the postcondition-before-business-outcome and business-outcome-before-postcondition ordering directly in the event sequence.

## 7. Architecture and boundaries

**Decision.** A modular monolith: one Node package, logical module boundaries (`contracts`, `surface`, `policy`, `replay`, `discovery`, `compiler`, `session`, `multitenant`, `catalog`, `mcp`) with no physical service boundaries between them. Each CLI entry point (`discover`, `replay`, `compile`, `promote`, `operator-console`, `mcp-server`, `catalog-demo`) is a separate OS process when it needs to be genuinely independent (the replay worker and the operator console *must* be separate processes for the handoff to be real) and otherwise a plain synchronous function call. No message queue, no separate database service, no container orchestration.

**Why a monolith, and why that's a defensible choice rather than a shortcut.** The brief states directly that scaling infrastructure isn't rewarded, and separately that "simpler is fine if justified." The justification here is architectural, not just expedient: the one seam that *would* need to become a real distributed system at production scale — session handling across many tenants — is already isolated behind a single abstraction (`SessionBroker`) that doesn't need to change shape to grow, only to be implemented differently underneath (a keyed pool instead of one evidence-directory's worth of files). That is the actual meaning of "not painted into a corner": the boundary is drawn in the right place today, even though what sits behind it today is the simplest thing that could be genuinely correct rather than the thing that would handle production load.

**Why sync/file-polling over a message queue for the handoff, specifically.** The handoff's real requirement is a *contract* — pause here, expose this session, resume when this one field flips — not a transport. A message queue would satisfy that contract but add a broker to run, a delivery-guarantee story, and a second place state could live, for a benefit (decoupling, back-pressure, retry) that has no load to justify it at N=1. File-based polling scoped to one run's evidence directory (`waitForResolution`, `readIntervention`) satisfies the identical contract with the simplest implementation that is still genuinely real — two separate OS processes, agreeing on a path instead of a queue topic, which is what actually matters for "is the handoff real," not what mediates the agreement. `docs/phase-2-scale.md` already states the corresponding invariant this leaves room for: a message transport, when one is introduced, carries events — it is never allowed to become the system of record, which the file-based version already isn't (the evidence directory is).

**Why CDP-based multi-process session sharing was still worth the complexity it does add.** This is the one place strict simplicity was *not* chosen over an out-of-process design, and that trade-off is deliberate: a same-process, in-memory "handoff" (an in-app modal pausing a script running in the same Node event loop) would have been simpler to build but would not have satisfied the brief's own literal requirement — "the same live session," provably, not a simulation of one running inside the same process as the thing being paused. The added complexity (a real CDP endpoint, a second connecting process, a file both processes agree to read) buys a claim that can actually be verified by a skeptical reviewer rather than taken on faith.

**Evidence.** `REPORT.md` §1's "modular monolith" framing; `docs/phase-2-scale.md`'s ten scaling invariants, none of which required a shape change in the code already built to remain true.

## The one thing that wasn't a choice: a genuine discovery run

The brief is explicit that this is not negotiable, and it wasn't treated as one. Every `evidence/discovery-*/` directory in this repository (`discovery-run`, `discovery-run-autocompile`, `discovery-run-explicit-target`, `discovery-handoff-demo`, among others) is a real `claude-sonnet-5` tool-use transcript against the live target app — genuine API calls, a real browser, real screenshots, a real trace of what the model decided and why at each step (`trace.jsonl`'s `modelRationale` field), not a scripted or hand-written stand-in. `docs/slices.md`'s Slice 6 entry and this project's own gap-closure history (the 3.1 and 3.6 reviews specifically) show these runs being used to find and fix real defects during development — a goal-text redaction leak, an accessible-name resolution bug, a structurally-impossible handoff path — which is only possible because the runs are real; a described or simulated run would have had nothing to find.

## What was deliberately mocked, and why

Per the brief's own standing allowance ("a well-designed seam is fine; mock deliberately and document what you mocked and why"), several pieces of this project are intentionally not full production implementations. Naming them here is the other half of that allowance — a mock left undocumented reads as an oversight; a mock stated plainly is a scope decision.

- **The operator console's UI.** Server-rendered HTML, no framework, refresh-based, exactly per the brief's own scope note ("a full real-time co-browsing operator console is out of scope... mock the operator UI if needed"). What is *not* mocked: the console is a genuinely separate OS process, attached via real CDP to the identical live session, acting on real controls and flipping a real file the suspended worker is actually polling. The seam that matters (the handoff mechanism, the control-transfer model) is real; only its visual polish is a stand-in.
- **A desktop surface.** Not implemented at all, by explicit brief instruction ("we do not expect you to implement... desktop support"). A concrete port plan — which schema fields need a new `SurfaceAdapter` versus need no change at all, which targeting rungs have a direct UIA analogue and which don't — is delivered as a design in `COMPLIANCE.md` instead.
- **A third multi-tenant layer (`VersionVariant`, for vendor-release differences distinct from tenant branding).** Not built, since only one vendor product version was ever in scope to exercise it against. Documented in `COMPLIANCE.md` as reusing `TenantBinding`'s exact override mechanism rather than needing a redesign — a one-more-instantiation gap, not an unknown.
- **`assistedRepair` (bounded, opt-in, single-step LLM recovery during replay).** The schema field exists and is validated; the recovery behavior behind it was never implemented, and it ships `enabled: false` on every artifact in this repo. This one is a genuine scope cut rather than a brief-mandated exclusion — worth stating plainly so it reads as a decision (keep the LLM out of the default replay path entirely, reserve the field for a future, deliberately narrow exception) rather than an unfinished feature.
- **Production secrets management.** `TenantBinding.authProfileRef` is a reference string, never a credential — resolving that reference to real material is explicitly a secrets-manager integration point, out of scope here and named as such in the schema's own comments.
- **Session pooling and message-queue infrastructure.** Explicitly not built, per `docs/phase-2-scale.md`'s own framing: building it now would be premature scaling infrastructure, not sound abstraction design, and the brief does not reward it.
